# Минимальный Feature-Sliced Design для фронтенда

Изначально приложение выросло из одного экрана, и плоская раскладка `components/` начала смешивать секции лендинга, доменные сущности и UI-кит. Разложили `apps/frontend/src` по всем слоям FSD: `app → pages → widgets → features → entities → shared`. На практике почти всё использовалось один раз: семь секций главной, карточка формата и две сущности из пары строк. Слои не давали переиспользования, только лишние `index.ts` и переходы между папками.

Решили оставить `app → pages → entities → shared`. Слой `entities` сохранён для `format`: он нужен и главной, и записи, задаёт `FormatId` и разбор query-параметра. Слои `widgets` и `features` не создаём, пока не появится реальное переиспользование или самостоятельное действие с состоянием. Секции главной — локальные компоненты `pages/home/ui/sections`, их контент — `pages/home/model/content.ts`. Шапка и подвал — layout приложения в `app/ui`.

Рассматривали полный FSD и строго три слоя (`app`, `pages`, `shared`). Полный FSD оказался дороже без выгоды на двух страницах. В строгом варианте форматы пришлось бы положить в `shared/config`, смешав конфиг приложения с доменными данными.

Последствия: меньше папок и публичных API; `widgets`/`features` добавляются только по мере необходимости; глубокие импорты и импорты вверх запрещены и проверяются тестом `src/__tests__/architecture.spec.ts`.
